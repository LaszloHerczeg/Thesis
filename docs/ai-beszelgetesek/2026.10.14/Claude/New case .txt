Q:
why did you use form.as_div?

A:
Mostly because it’s the shortest way to render the whole form correctly. {{ form.as_div }} outputs every field with its label, its validation errors and any help text, so the template stays tiny while the form is still being built.

There are two more specific reasons:

Valid, accessible HTML. as_div wraps each field in a plain <div>, unlike as_table (table layout for non-tabular content) or as_p (it can produce invalid HTML when a widget renders block elements inside the <p>). It’s Django’s recommended layout, and since Django 5.0 a plain {{ form }} renders exactly the same thing.
It handles your “same group” requirement. With the div layout, Django wraps radio and checkbox widgets in a <fieldset> with a <legend>. So the three language checkboxes sit in one labelled group, and so do the three format radio buttons, without any extra code.

The trade-offs: as_div needs Django 4.1 or newer, and you get little control over layout. You can’t easily reorder pieces, add CSS classes around a single field, or put “Ft” anywhere other than where the widget renders it. If you’re on an older Django or want full control over the markup, the usual alternative is to render each field yourself:

django
<div>
  {{ form.description.label_tag }}
  {{ form.description }}
  {{ form.description.errors }}
</div>

Q:
so {{form}} is the same as {{form.as_div}}?

A:
Yes, on Django 5.0 and newer, as long as nothing changes the form’s default template.

Django 5.0+: {{ form }} renders the form’s default template, and that default is the div layout. So the output is identical to {{ form.as_div }}.
Django 4.1 and 4.2: {{ form }} still renders the old table layout, the same as {{ form.as_table }}. as_div exists, but you have to call it explicitly.
Before 4.1: {{ form }} is the table layout, and as_div doesn’t exist at all.

The exception is a customised default: a template_name set on the form class, or a custom FORM_RENDERER with a different form_template_name in settings. In those cases {{ form }} uses that template, while {{ form.as_div }} always uses Django’s built-in div template.

So if you’re on Django 5+ with default settings, you can replace {{ form.as_div }} with {{ form }} and nothing will change. Keeping as_div just makes the layout explicit and independent of those settings.

Q:
The form does not display any error messages when I leave the description field empty. Why is that?

A:
With the files I gave you, the error only appears after you press Submit, and that’s because of the novalidate attribute I put on the <form> tag.

Django adds required, minlength="30" and maxlength="5000" to the description field’s HTML, and a browser normally uses these to stop the submit and show a “Please fill out this field” bubble. novalidate turns that browser check off, so nothing happens on the page while you type or leave the field. The form is sent to the server, Django validates it, and the page reloads with “This field is required.” above the description field.

If you want the immediate browser message, remove novalidate:

html
<form method="post" id="case-form">

Django still validates on the server either way, so you’re safe even if someone bypasses the browser check. The browser bubbles look different in each browser and their wording isn’t controlled by Django, which is why I’d left them off.

If you did press Submit and still saw no message, something else is going on. The usual causes are:

The view replaces the failed form. It has to pass the same bound form back to the template. A line like form = CaseForm() after the if form.is_valid(): block erases the errors.
The template renders fields one by one and leaves out {{ form.description.errors }}.
Django is older than 4.1. There {{ form.as_div }} renders nothing at all; use {{ form }} or {{ form.as_p }} instead.

If none of these fits, paste your current view and template and I’ll find it.
